# Schema changes are Alembic revisions, applied by a one-shot service before the bot starts

The database's schema is changed only by Alembic revisions in `src/winter_dragon/migrations/versions/`, autogenerated from the models, reviewed and committed. `docker compose up` dumps the database, runs `python -m winter_dragon.migrations upgrade` in a one-shot `migrate` service, and starts `bot` and `web` only when it succeeded. A cog no longer creates its tables in a migrated database; it checks they exist and refuses to load when one is missing. CI applies every revision to an empty Postgres and fails when the models have changes no revision covers.

Before this, each cog ran `create_all` for its tables when it loaded, and `ensure_lifecycle_columns` added columns the lifecycle models gained. That can only add: dropped and renamed columns stayed behind as `NOT NULL` columns the models never set, so inserts failed in production (autochannel hubs, stats channels), and a hot reload could create a table in the live database before any migration existed for it.

## Considered Options

- **Diff the models against the database at startup and apply the safe changes, with no revision files.** Rejected: drops and renames still need hand work, nothing records what was applied, and an accidental model edit changes the live schema with no review.
- **Keep `create_all`, and fix drift by hand when it shows up.** Rejected: that is what failed; drift only surfaces as errors in production.
- **Run the migrations inside the bot's startup.** Rejected: the dashboard needs them too, and a failed migration would leave a bot running half-started. A one-shot service fails once, visibly, and keeps both from starting.
- **One revision history per cog (Alembic branches).** Rejected: the cogs share a database and one deployment, and branches make every revision name its dependencies.

## Consequences

- A model change needs its revision in the same commit; CI's `check` fails otherwise, and the bot refuses to load a cog whose table is missing.
- Revisions are generated against a scratch Postgres, never the live database, and read before committing: autogenerate writes a rename as a drop and an add, and leaves Postgres enum types behind on downgrade.
- Migrations run on `docker compose up`, not when Docker restarts a container, so new code is deployed with `docker compose up -d --build`.
- Every `up` takes a `pre-migrate` dump, and `backup-daily` takes one a day; the newest 14 of each are kept in `./backups/`.
- The sqlite test bot and the tests don't use migrations: there `ensure_tables` still creates the tables.
